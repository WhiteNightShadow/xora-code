## 1. 审查：现在的样子

### 1.1 数据（用户真实数据的副本，2026-11-10，30段对话、2888次模型请求）

| 看什么 | 数字 | 说明 |
|---|---|---|
| 每次请求的输入 | 平均11.2万token，最大29.4万；缓存命中97.5% | 花费靠缓存压住了，但模型每一步都在十几万token里找重点 |
| 最长的一轮 | 189次请求，上下文18.4万→26万（MiniMax-M3.1-Flash） | 设置里的上下文上限是51.2万，80%才压缩，所以几乎不压 |
| 压缩 | 只发生2次：6.2万→2.7千、9.9万→2.7千 | 23倍的压缩比，丢得多；第二次压缩会把第一次的摘要再摘要一遍 |
| 工具调用 | bash 1343次、read 263、edit 69、write 48、grep 42、web 71 | 上下文里大半是命令输出 |
| 记忆 | `remember` 3次，`recall` 0次；十天只有3条笔记 | 写记忆全靠模型主动调工具，它几乎不调 |
| 谁有记忆 | 只有成员、团队任务、工作流步骤的线程 | 用户自己开的普通对话占50.7%的请求，没有记忆、没有`remember`/`recall`；总助手也没有 |

### 1.2 问题

1. **记忆没在起作用**：只给成员线程；写入靠模型自觉；文件写满16000字就丢最旧的一条，不看重要不重要；`recall`每次把所有笔记文件读一遍做关键词匹配；没有出处、没有有效期，过时的笔记和新的并存。
2. **长任务的上下文没人管**：触发线跟着模型窗口走（51.2万的80%），远在质量开始下降之后；真压起来是散文摘要，摘要套摘要会漂移；`todo`计划不在上下文里，压缩后模型就看不到自己的计划。
3. **缓存在白白丢**：
   - 上下文在60%～80%之间时，每来一个新工具结果，“保留最近6个”的窗口就往后挪一格，改掉一条更早的消息，缓存从那里断开，一次请求一次。
   - 摘要是另起的一个请求（另一套系统提示词、不带工具），读不到对话的缓存，整段按全价算。
   - 总助手的“现在的情况”每轮都变，却放在系统提示词里，每轮开头整段对话重算。
4. **在Claude上可能直接出错**：Claude 5系列要求回传的思考块原样不动，改动更早的工具结果（第2层裁剪）会让后面的思考块失效；2026-08-31以后的账号会返回400（调研报告读文档和代码得出，待复现）。
5. **两套状态没打通**：团队主管被唤醒时拿的是结构化的运行状态（任务账本+每张卡的状态，06第29节），普通对话压缩时却只有散文摘要。
6. **代码往上叠**：host有2.7万行，`team.ts`一个文件5238行、107个私有方法（规划、派卡、执行、验收、巡检、升档、整合、报告、打分都在里面）；记忆写在`members.ts`里，和组织、名册、例行任务混在一起；拼提示词的逻辑在`turns.ts`里。

## 2. 调研结论

三份调研（super agent架构、上下文压缩、agent记忆），每条结论都有出处，原始报告和笔记存在会话的临时目录。要点：

### 2.1 上下文

- **长上下文本身就会变差**：所有测过的模型都随输入变长而变差，远没到窗口上限就开始（Chroma, Context Rot, 2025-07）；Gemini 2.5的agent在上下文过10万后开始重复旧动作。
- **观察遮蔽（用占位符换掉旧的工具输出）和摘要效果差不多，便宜一半**（JetBrains, The Complexity Trap, arXiv 2508.21433）；但每次挪窗口都会让缓存断一截，要成批做。
- **摘要套摘要会漂移、会塌缩**（ACE：整体重写把18282 token的手册压成122 token，准确率低于不用手册）；Codex也提醒多次压缩会降低准确率；Amp干脆用“交接到新对话”替代压缩。
- **结构化状态比散文摘要好**：Factory的评测里所有摘要方法在“改过哪些文件”这一项都≤2.45/5，建议由程序记录文件状态；Gemini CLI用`<state_snapshot>`并做确定性校验；Anthropic用JSON功能清单+进度日志，模型更少误改。
- **丢掉的东西要能找回**：大结果第一次就落盘，上下文里留引用号、大小和头尾（Cursor、LangChain、Gemini CLI、Manus都这样做）；“请重跑一次”的占位符会引来重复执行和副作用。
- **压缩请求要和当前请求同前缀**（同模型、同系统提示词、同工具、同消息，最后追加压缩指令），才能读到缓存（Claude Code团队：Prompt caching is everything, 2026-04）。
- **变化的内容放最后**：提醒、状态变化、日期放在最新的工具结果后面，永远不放系统提示词（Manus、Claude Code）。

### 2.2 记忆

- **主流编程agent都不用知识图谱做记忆**：Claude Code、Codex、Cursor、Devin、Copilot都是纯文本——一小层常驻加载、其余按需读取，外加某种保鲜机制。Mem0在2026-04把图存储从开源版里拿掉了。
- **图结构本身没有被证明有用**：同等预算下图记忆不如平铺的笔记（F1 0.417对0.468），差别“来自基础设置而不是架构创新”（Does Memory Need Graphs?, 2026-02）。真正起作用的是这几样，它们常和图打包出现：
  1. 写入时就解决新旧冲突（旧的关掉有效期，不删）；
  2. 每条带有效期和出处；
  3. 保留原始对话可搜；
  4. 让agent自己搜（agentic search：普通编程agent搜文件69.3%，最好的RAG 48.5%）。
- **对编程的帮助有限且要靠写得好**：经过验证、提炼的经验能提高1～7个百分点；12组“现成记忆系统+求解器”里11组没赢过不用记忆；模型自己写的技能平均没用，人整理过的有用。
- **风险是真的**：记忆投毒（OWASP ASI06）、把用户的说法记得比用户还肯定、过时事实。

**关于“知识图谱”的结论**：不建图数据库，也不做“每次写入都抽实体、建三元组”的重流程；做一个**带有效期和出处的事实账本**，事实挂在实体（文件、命令、模块、接口、人、偏好）上，靠实体做一跳关联——这就是够用的轻量图，存在SQLite里，读的时候不调模型。同样的思路用在上下文上：**任务账本**是一张图形状的状态（目标、约束、决定、任务、文件、命令、错误、问题，节点带编号、状态和出处，边是“改了/因为/阻塞/解决”），由程序记录能观察到的，压缩时由模型补判断，取代散文摘要。

### 2.3 super agent架构（2025下半年～2026-11）

- **先把上下文做好，再加agent**：同一个模型只改上下文管理，BrowseComp从60.6到74.9（Kimi K2.5，完整swarm是78.4），GLM-5从62.0到75.9；按需加载工具（Tool Search）把预载的工具定义从约7.7万token降到8.7千，Opus 4从49%升到74%。
- **单写者，审查者独立**：并行写同一份代码的swarm至今不行（Cognition 2026-04；Cursor 2026-01：20个agent靠锁协作，只有两三个的吞吐）；审查者不共享上下文，只拿diff和任务卡，自己去跑产物（Anthropic 2026-03：模型给自己的活打分系统性偏高）。
- **路由要薄，后续按归属直达**：DeepSeek的Router只做冷启动分派；一件事有了负责的Worker，后面的消息直接进它的队列。没有直达时Router的决策多约30%、缓存读多37%（合成测试，DeepSeek说是初步结果）。
- **一种工作项，阶段是算出来的**：DeepSeek用Ticket、Assignment、Report三种记录，阶段由一张“先匹配先得”的表从记录算出（待答复→待审→受阻或失败→排队→空闲→进行中），不从执行者的自由文本推断；重启恢复就是重算一遍。
- **授权跟着工作走**：每次接活存一份不可变的Mandate（策略版本、范围、强度）；没人要求的活先只记录不执行。
- **审批看动作不看叙述**：Claude Code的auto模式分类器只看用户消息和工具调用，去掉助手的话，“免得agent把分类器说服”；连续3次或累计20次被拒就找人。
- **每个harness部件都要按模型重新验证**：Anthropic 2026-04的一次质量回退来自三处harness改动（默认effort调低、思考清理每轮都触发、≤25字的回复规则）；Sonnet 4.5需要的上下文重置到Opus 4.5上成了累赘。提醒频率、压缩阈值、规划步骤要能按模型开关，并用真实失败的任务做消融。
- **记忆＝原文可搜＋一小份常驻＋离线整理**（Anthropic 2026-11-06）：原文检索是基础，常驻部分要小，离线“做梦”整理以diff的形式提议修改；并发写同一个文件会丢事实（57条丢16条），写入要串行。
- **反模式**：并行写者；一个agent包揽所有职责；简单问题派几十个子agent；让模型自己决定要不要委派（中性提示下单会话从不委派）；自评自审、过早宣布完成；从自由文本推断状态；运行中改工具列表；长期背诵todo（Manus三分之一的动作花在更新todo上）。

**对Xora的取舍**：Xora已经有DeepSeek式的总助手、任务账本、worktree单写者、验收、巡检和steer队列（06第20、23、29节），方向是对的。这次只做排在第一的上下文和记忆；卡片订阅直达、统一工作项、按模型开关的harness部件、审批只看动作放进第2期（第5节）。

## 3. 要保留的特色

- 总助手是唯一入口：直接回答，或者把活交给成员、团队、工作流，跟进卡片跟到结果。
- 组织树：成员像公司一样分组织，负责人带组织，提示词沿组织链继承，组织在每个项目里有自己的笔记。
- 主管带队的团队任务：任务卡（文件归属、验收命令、预算）、阶段、巡检、升档、整合、交付报告（三段式）、主管打分。
- 先给结论的工作流；审批由主管代审，大批量删除和删库才找人；每一轮的改动可审可撤。
- 多模型中立（国产模型、本地模型、订阅）、花费按价格表核算；中文优先；应用包签名热更新。

这次的改动都落在这些特色之下：账本是主管运行状态的推广，记忆按组织树分范围。

## 4. 设计

### 4.1 原则

**状态进账本，原文可找回，变化放末尾。**

- 能观察到的事由程序记（读了哪个文件、改了什么、命令和退出码），不交给模型去复述；模型只补判断（决定、约束、结论）。
- 被挤出上下文的东西都有引用号，原文在会话文件里，随时取回，不用重跑。
- 系统提示词和工具列表在一段对话里保持不变；每轮变化的信息（状态、提醒、日期）跟在最新消息的后面。

### 4.2 引擎：任务账本（Task Ledger）

每个会话一份。能观察到的部分每次从完整历史算出来，不另存；模型写的判断随压缩记录一起存（`compaction`记录多了`judgments`和`narratives`），重启和回退都能还原。

| 种类 | 谁写 | 内容 |
|---|---|---|
| request | 程序 | 发给模型的每条消息原文（用户的；host交下来的活里是host的），带引用号，从新到旧，最多占对话空间的15%（封顶2万token），较早的每条最多4千token；最新那条再长也不丢，只截断并给引用号；环境块、提醒、hook输出、host附加的数据块不算，附件只写文件名 |
| plan | 程序 | `todo`清单（已有） |
| file | 程序 | 路径、读了几次、改了几次、最近一次的引用号（`read`/`lsp`/`edit`/`multi_edit`/`write`/`apply_patch`） |
| command | 程序 | 最近12条命令、成败、第一处错误、引用号 |
| other | 程序 | 其它工具调用（搜索、网页、MCP、host工具）最近12条：做了什么、成败、引用号——它们跑过，有副作用的不能再跑一遍 |
| error | 程序 | 还没修好的失败；之后同一个工具对同一个对象成功了就关掉 |
| job | 程序 | 还在跑的后台任务 |
| constraint / decision / fact / question / deadend | 压缩时由模型写 | 一句话；约束必须逐字引用发给模型的某条消息；决定带理由；编号由引擎给（C1、D2…）；只增不删，过时的标“已完成”或“被取代” |

- 平时不在每轮背诵账本（Manus的教训）；完整账本只在压缩后的那条消息里出现。
- 渲染是确定性的：同样的记录渲染出同样的文字，各类有条数上限。
- 工具结果按位置和调用配对，不只看id：有的服务商每次回复都从`call_0`重新编号。
- 账本从上次“重新开始”的地方观察历史：团队主管带着运行状态被重新唤醒（06第29节）以后，之前的消息和失败不再算；host给的那份状态作为“重新开始时的情况”整段保留（最多6千字），直到下一次重新开始。
- 所有截断都不拆代理对（emoji）：孤立的代理字符会让请求被拒（Anthropic返回400，而且不重试）。

### 4.3 引擎：可找回的工具结果

- 已有：bash输出超过3万字时截中间、全文落盘、给路径。保留。
- 被遮蔽的工具结果不再是“请重跑”，而是一行引用：`[#R12 bash "npm test" · failed · 4.1k chars · Error: … — masked to save context; tool_output("R12") returns it]`；失败的结果在引用里留着第一处错误。
- 新工具`tool_output`（只读，不用审批）：按引用号取回原文，可以带`offset/limit`或`grep`；读的是会话里存着的原文，不重跑。消息和模型自己的回复也有引用号，状态里截断或省略的消息能原样取回。任何角色的工具白名单都不隐藏它。

### 4.4 引擎：遮蔽和压缩

- **预算**：`min(模型窗口, 上下文上限, 工作上下文)`减去回复的余量。“工作上下文”是新设置，默认16万token：质量早在窗口用满前就开始下降，用户把上限设得很大也不影响这里。系统提示词和工具定义计入估算（厂商的计数里本来就有，单位要一致）；它们压不掉，所以预算至少给对话留3.2万token的空间（不超过窗口），工具定义很多的线程不会每步都压缩。
- **成批遮蔽**：用到预算的60%时，如果能腾出至少20%，一次把除最近8个以外的工具结果都换成引用；之后冻结到下次压缩，不再一格一格地挪。
- **压缩**（用到80%时；先试遮蔽，遮蔽后回到80%以下就不压）：
  - 同前缀分叉：同模型、同系统提示词、同工具、同消息，指令加在最后一条用户或工具消息的末尾（有的服务商不收紧跟在工具结果后的用户消息），读得到缓存。
  - 模型只补判断：一段250字以内的经过，和一个JSON块——对账本的增量（新增约束、决定、事实、问题、死路，按编号关掉旧条目）。程序合并，编号稳定，不整体重写。
  - 确定性校验：JSON能解析、条目合法、约束确实引用了用户原话、每次最多12条、和已有条目重复的不再加。不过的条目丢掉；模型请求失败就只用账本（程序记录的部分永远在）。
  - 保留最近几步原文：最多占对话空间15%（封顶2.4万）且不超过当前对话的四分之一；切点只在消息或模型回复之前，不会把工具调用和结果拆开；**模型还没看过的部分**（最近一次调用的结果、刚发来的消息）多大都保留；切点之前只有发给模型的消息时不压。用户手动点“立即压缩”时只保留没看过的部分。
  - 换用备用模型：按备用模型自己的预算管理上下文（它的窗口可能更小），需要时向备用模型要它那一份（第4级）；不再每次换模型都压缩——主模型一直不可用时那样会把上下文锁死成只剩状态。另一家的思考内容本来就由各服务商的适配层丢掉。
  - 1.3以前的散文摘要、团队主管被唤醒时的运行状态，都作为“重新开始时的情况”整段保留，不再当成“经过”截短、过两次就丢。
  - 模型写的账本逐条校验：一条不合规只丢这一条；状态值认中英文的同义写法；`...`、`<一句话>`这类照抄表单的占位文字不收；表单示例里没有能当真的编号。
- **压缩后的上下文**：状态消息（`<task_state>`：用户的消息、计划、约束/决定/事实/问题/死路、文件、命令、未修好的失败、后台任务、最近两段经过）+保留的最近几步原文。最近改过的文件不自动重读，账本里列着引用号。
- **Claude的思考块**：遮蔽和压缩是仅有的两个改动历史的地方，次数因为成批而很少；保留的尾巴里同一模型的思考块照原样回传。
- **连续压缩3次以上**：状态消息里建议把剩下的活交接到新对话（第2期做成按钮）。

### 4.5 host：拼上下文

- 每轮变化的东西不进系统提示词：`HostToolProvider.turnNote`在用户每条消息后面附一个`<host_note>`数据块（界面上不显示）。总助手的“现在的情况”改走这里，每条消息都附完整的一份（编辑、回退、取消、压缩之后，之前附的可能已不在上下文里，所以不做“没变就省略”），报告只附最近结束的3份、每份截到800字，其余用`work_status`查；它的系统提示词整段对话保持不变。
- host附加的说明（@成员的交接提示）也包在`<host_note>`里：引擎的状态不会把它当成用户的话，UserPromptSubmit hook拿到的也只是用户写的部分。
- 把拼层整个从`turns.ts`拆出去放到第2期，和`team.ts`的拆分一起做；这次只加了十几行。

### 4.6 记忆：人人都有的记忆

- **范围**：用户的偏好（新，`orgs/default/user.md`）→组织在项目里的笔记→项目全体的笔记→成员的通用笔记→成员在项目里的笔记。
- **谁读什么**：Xora引擎的线程，除了团队和工作流运行里的（它们的提供者自己管记忆），都有记忆：
  - 普通对话：用户的偏好+这个项目全体的笔记；
  - 总助手：用户的偏好（它不属于哪个项目）；
  - 成员的线程：原来的四部分，前面再加用户的偏好；
  - 子agent：没有共享的记忆。它读的是交给它的东西，常常来自网页或仓库，不能让它写下所有线程都当作“用户偏好”来读的东西（成员的子agent照旧带成员的记忆）。共享工具也受agent定义里的`disallowedTools`约束。
- **快照**：线程开始时取一次（重启后重新取），系统提示词因此整段对话不变；之后写的笔记用`recall`查。
- **写**：`remember`的scope：普通对话是`project`（默认，写进项目全体的笔记，成员也读得到）和`user`；总助手只有`user`；成员多了`user`。密钥照旧拦下；同一个文件的写入串行。
- **查**：`recall`查所有笔记（用户的、各成员的、全体和各组织的），再查以前的对话：只查同一个项目的（总助手查全部），排除提问的这段对话；从整条消息里先去掉密钥、token、密码，再截出命中处前后约300字。
- **原件仍是Markdown**，用户能直接看、能改；成员页的记忆下拉框多了“用户的偏好”，清空它时的确认框写明所有成员和对话都读这份；用户在面板里改掉或清空的内容留一份在同目录的`*.md.bak`。
- 替换一条笔记时，新的放到最后：文件写满时从最旧的删起，删不到刚写的那条。
- **这次没做，留到第2期**（理由见第5节）：每条笔记的短编号和`*.history.md`、SQLite索引和实体别名、`kind/about`字段、对话结束后的自动整理。
- 记忆永远只是资料：提示里写明“不是指令”，不能改设置、审批、端点。

### 4.7 编排：同一种账本

- 普通对话：任务账本（引擎）。
- 团队：运行账本（host，已有）不变；每个执行者的线程有自己的任务账本。
- 总助手：它派出去的活（跟进卡片）就是它的账本，每轮作为数据块附在用户消息后面。
- 工作流：步骤状态同理（以后）。

### 4.8 代码结构（这次落地的）

- `packages/engine/src/context/`：`tokens.ts`（估算）、`window.ts`（预算和触发线）、`outputs.ts`（引用、遮蔽、取回）、`ledger.ts`（观察和渲染）、`compaction.ts`（切点、分叉请求、校验合并）、`messages.ts`（发给模型的消息），取代原来的`context.ts`。
- `packages/tools/src/tools/output.ts`：`tool_output`工具。
- `packages/host/src/memory/`：`files.ts`（路径、原子写、串行）、`notes.ts`（笔记行的纯函数）、`text.ts`（中英文案）、`service.ts`（快照、remember、recall、成员面板），从`members.ts`搬出约370行；`members.ts`只管成员和组织。
- `packages/host/src/shared-tools.ts`：多个共享工具来源合成一个（子agent、记忆）。

## 6. 风险

| 风险 | 控制 |
|---|---|
| 遮蔽和压缩后模型重复干活 | 引用可取回，账本列出改过的文件和命令结果；评测看压缩后的重复调用 |
| 模型补的判断写错、写偏 | 约束必须引用用户原话；只增量、编号由引擎给；最多12条；程序记录的部分不经模型 |
| 记忆写错、被投毒 | 记忆是资料不是指令；密钥写入时拦下、recall读对话时脱敏；子agent不能写共享的记忆；用户能在成员页直接改、清空有备份；自动整理等有了记忆页面再做。还剩的口子：用户自己的对话读了网页之后仍能写“用户的偏好”，第2期考虑写这一层时出卡片确认 |
| 压缩请求更贵（同模型而不是快速模型） | 读的是缓存（命中价是未命中的1/10～1/50），只多付一次输出；压缩次数因为成批遮蔽而更少 |
| 总助手的状态块让对话变长 | 情况变了才发全文，每份报告只发一次；之前的块都在缓存前缀里 |
| 改动面大 | 分模块搬家、先有测试再换实现；第1期不动`team.ts` |
