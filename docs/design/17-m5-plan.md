- 日期：2026-10-30
- 状态：实施中，进度见第4节。本文把M5拆成工作包，并记录相对设计稿（06第11、12节，11第7节）的调整。
- 分支：在`next`上开发，本地提交，推送和合并回`main`等用户确认。

## 1. 相对设计稿的调整

| 项 | 设计稿 | 调整为 | 理由 |
|---|---|---|---|
| 步骤在哪个目录做 | 未定 | 都在项目目录里做，不另开worktree；并行的步骤共用这个目录 | 主管步骤交给团队运行，团队把各自的worktree整合回项目目录，后面的步骤要能接着用；写同一批文件的步骤用`needs`排先后 |
| 并行组、条件分支 | 单独的步骤类型 | 用`needs`表达并行：依赖都完成的步骤同时开始（上限`concurrency`，默认3）；条件用`if`，写一个引用，或者一个引用和一个字面量比较 | 少一种类型；`if`能覆盖“前一步失败才做”这类分支 |
| agent步骤怎么交结果 | 结构化结果 | host给这个线程一个`step_result`工具，交summary和声明过的outputs；漏交就再要一次，还缺就算失败 | 和团队的`deliver`一样走host工具，不靠解析回复里的json |
| 人工关卡、失败后问人 | 人工关卡 | 都做成审批卡片，挂在这次运行自己的线程上；关卡被拒绝就停止运行，过期了再问一次 | 复用“等我处理”和审批卡片，不用另做一套 |
| 命令里的模板值 | 未定 | 代入验收命令和命令步骤时，每个值都按shell的规则加引号（mac、linux用单引号，windows用powershell的单引号） | 输入和agent交回的值不能变成命令的一部分 |
| 失败策略 | 重试、升档、换agent、跳过、终止 | 按这个顺序：`retries`次带反馈重试，`escalate`升一档，`agent`换人，最后`finally`：`abort`终止、`skip`跳过、`ask`问人 | 和团队的“退回→升档→换人→问人”一致 |
| 定时与触发生效的条件 | 应用在托盘运行时 | 另加：项目里的工作流要用户逐个启用自动运行；启用时记下文件的哈希，文件改了（拉了新代码、改了文件）就停用，等用户重新确认 | 不能让一个仓库靠一个文件就在用户机器上定时跑东西 |
| 无人值守运行的限制 | 只走api通道，受预算约束 | 沿用团队L3的检查：只走api通道、必须有预算、不能有`full`权限的agent；另外要求开头用到的模型都能计价，否则不启动，记一条失败的运行说明原因 | 没有价格表的模型花费记不上，预算形同虚设 |
| 预算算哪些 | 每次运行 | 这次运行自己的agent步骤，加上主管步骤启动的团队运行和子工作流 | 主管步骤和子工作流的钱也是这次运行花的 |
| 重启 | 从未完成的步骤继续 | 没结束的运行在重启后暂停（排队等空闲时段的照常等），点继续从没完成的步骤接着做；做到一半的agent步骤回到原来的线程里继续，主管步骤继续原来的团队运行 | 和团队运行一致；完成的步骤不重跑 |
| 用户级工作流 | 未定 | `<数据目录>/workflows/*.yaml`，任何项目都能手动运行；自动运行只给项目里的工作流 | 用户级的没有固定项目可绑 |
| 团队对话 | 未细化 | 一次团队运行里的消息按时间记一份：主管发给成员的、成员问主管和得到的回答、用户插的话、竞争假设模式里成员之间的质疑。团队视图加“对话”页签，用户可以给主管或某个任务发消息：发给主管的会唤醒它处理，发给成员的在它下一轮开始时带上 | 用户的话是指示（可以改目标、加约束），不是对某个操作的批准，审批照旧走卡片（06第7节“消息不是授权”） |
| 竞争假设模式 | 排障、调研时打开“互相质疑” | 团队运行加一个模式：主管先列2～4个可能的原因，每个原因一张只读的调查卡，验收是交出支持和反对的证据；成员可以给别的调查卡发质疑，对方下一轮回应（每人有次数上限）；主管按证据判定哪个成立，再决定建修复卡还是直接交结论；交付报告逐条列出假设和结论 | 参照claude code用竞争假设排查根因的做法；只读卡互不冲突，可以并行 |
| 从线程沉淀 | 沉淀为工作流或skill | 线程菜单里发起：新开一个线程，把原线程的记录交给agent，按extension-creator里的格式写文件；写文件走审批卡片，用户先看草稿；工作流草稿用`workflow_check`工具检查到能解析为止 | 和“用对话创建扩展”同一套做法，不另做向导 |

## 2. 工作包

| 编号 | 内容 | 落点 |

## 3. 验收

M5的验收标准（14第2节）：一条三步工作流（复现→修复→审查）能中断后恢复；定时任务只走api通道，并受预算约束。
