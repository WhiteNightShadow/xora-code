# 19｜组织树：组织、成员、记忆、评分（2026-11-04）

这份文档取代06第24节里“小组”的说法：小组就是这里的组织。和06第19、21节不一致的地方以这里为准（记忆每轮现读改成线程开始时快照，组长改叫负责人）。

## 0. 用户要求

2026-11-04用户提的：

1. 团队结构是横向的树状图：最左边是“我/总助手”，往右是组织；组织下面可以建多个子组织，子组织里可以建成员。
2. 每个组织、每个成员都有自己的目录，按项目存放记忆；组织和成员各有提示词，可以改。

3. 建组织、建成员就在当前页面弹个窗填完，不开新对话。
4. 点一个成员，只看到：名字、提示词、最近参与了哪些项目、主管评分（满分100）、token消耗。
5. 要梳理组织怎么设计、记忆怎么存、彼此怎么配合，参考github和推特上的资料，再请一个agent评估方案，纠正后开始迭代。

## 3. 评估后的修正（2026-11-04）

初稿交给一个独立的agent对照代码评估，核实后采纳的主要修正：

1. **子组织负责人不接卡**：主管角色没有交付和写文件的工具，团队运行也不把卡派给主管（`team.ts`的staff、`team-agents.ts`的`cardProblem`）。交给一个组织的运行，由这棵子树里**非主管角色**的成员干活。
2. **“谁是主管”只有一处说了算**：`leadOf(组织)`逐级向上找负责人，`supervisorOf(成员)`给出一个成员的主管（到根就是总助手）。不再拿名册里“第一个主管角色的成员”兜底：组织和上级都没有负责人时，“交给这个组织”不可用，提示先设负责人。
3. **记忆层不再每轮重读**：记忆层在系统提示词里，每写一条笔记，下一轮整段历史的缓存都失效。改成线程开始时取一次快照，之后新写的笔记用`recall`查；记忆总预算保持9500字，只重新分配。
4. **token按成员记账**：主管代审、团队报告这类直接调模型的请求记在被审成员的线程上，按线程归属会把主管的花费算给成员。`usage_events`加`member_id`列和索引，记账时就定好算谁的。
5. **评分要稳**：分数由host按事实算的基础分，加主管模型±10的调整组成；运行报告写好后一次请求打完，状态存下来，重启后补打，不重复记，打不了就跳过、不编分数。v1只给团队任务卡打分。
6. **组织树的约束**：改上级要防环，挪完层数仍不超过3；名字全局唯一；负责人不能同时是别的组织的组员；删掉负责人就清空负责人，不拦着；回退到1.1.0不能把树压平（第4节）。
7. **界面别太宽**：成员是组织节点里的一行，不单独占一列；直属成员挂在一个“直属成员”节点下；节点上的“+”和“⋯”一直显示，不只在悬停时出现。
8. **v1不做的**：组织通用记忆和只有负责人能写的作用域、上级组织的记忆进提示词、多层转派、带队分、按分数派活、派活评分、运行后的记忆整理。

## 4. 模型：根、组织、成员

- **根**：我和总助手。用户只跟总助手说话（06第23节），总助手按组织树把活交给某个组织或某个成员。根不是组织，没有负责人；直接挂在根下的成员叫“直属成员”，它们的主管是总助手。
- **组织**：名字、一句话说明、组织提示词、负责人（可以空着），可以有子组织和成员。最多三层（组织→子组织→再下一层）：层数再多，派活要转几手，上下文一层层丢，界面也太宽。
  - 代码里沿用`OrgGroup`（06第24节的小组），加`parentId`；界面上叫组织、子组织。原来的小组就是第一层组织。
  - **负责人**：主管角色的成员，带这个组织的活：拆卡、派给子树里的成员、阶段评审、验收、打分。一个成员最多当一个组织的负责人，也不能同时是别的组织的组员。
  - **`leadOf(组织)`**：这个组织的负责人，没有就逐级往上找；一路都没有就是没有。
- **成员**：最多在一个组织里；不在任何组织里的是直属成员。主管角色的成员只当负责人，不当组员。
  - **`supervisorOf(成员)`**：它所在组织的`leadOf`；它自己是负责人时，是上级组织的`leadOf`；都没有就是总助手。评分、代审、界面上的“主管”都按它。
- **约束**：改上级时不能挂到自己或自己的子组织下面，挪完整棵子树的层数仍不超过3；组织名全局唯一（总助手按名字找组织）。
- **删除组织**：子组织和组员挪到上一级（第一层组织的挪成直属），负责人变成直属；组织目录移到`orgs/default/.trash/groups/<id>-<时间>/`，以后同名的新组织不会接着用旧的提示词和记忆。新组织的id不和回收站外残留的目录重名。

## 5. 存放：每个组织、每个成员一个目录

```
<数据目录>/orgs/default/
  org.md                    全体提示词：frontmatter（档位、预算等）+正文，正文对所有组织和成员生效
  agents/<成员id>.md        成员定义：frontmatter（名字、角色、档位、模型、权限、skill、mcp）+正文是成员提示词
  groups.json               组织树（version 2）：每个组织的id、名字、说明、parentId、负责人、组员
  memory/<项目id>.md        全体·项目记忆（原“团队记忆”）
  groups/<组织id>/          组织目录（新）
    prompt.md               组织提示词
    projects/<项目id>.md    组织在某个项目里的记忆
    names.json              项目id对应的显示名
<数据目录>/members/<成员id>/ 成员目录（已有）
  memory.md                 成员的通用记忆
  projects/<项目id>.md      成员在某个项目里的记忆
  routines.json             例行任务
```

- 成员定义留在`agents/`：团队运行、项目里的`.xora/agents`覆盖、内置成员的覆盖文件都按这个目录加载（`@xora/workflows`的`load.ts`），挪走要改加载器、迁移用户文件，换来的只是“定义和记忆在同一个文件夹”。界面里看不出区别。
- 每条笔记开头本来就有`[项目名 日期]`，打开文件能看出是哪个项目；文件名还是项目id，显示名记在`names.json`。
- **groups.json兼容**：写`version: 2`；没有负责人时写`leaderId: ""`（1.1.0读的时候不会丢掉这个组）；第一次按新格式写之前，把旧文件备份成`groups.v1.json`。1.1.0读新文件时不认`parentId`，子组织会显示成第一层组织，不丢人。
- 评分不是记忆，存在数据库里（第9节）。

## 6. 提示词分层

在08第1节、06第4节的基础上，组织层变成一条链：

```
系统（xora）→ 用户全局 → 全体提示词（org.md正文）→ 第一层组织 → 子组织 → … → 成员所在的组织
→ 成员提示词、skill、MCP → 记忆（快照）→ 项目（AGENTS.md、个人项目提示词）→ 会话 → 任务
```

- 组织链是一层`group_instructions`，每个组织一个小标题（“组织：研发中心”“组织：研发中心/前端组”）。每个组织的提示词保存时限3000字，不在运行时截断。
- 一个成员拿到的是它自己所在组织的链；团队运行里，它的组织不在运行所属组织下面时（比如上级负责人带子组织的活、用户点名别的组织的人），拿运行所属组织的链。同一个组织的成员共享这段前缀。
- 组织链在线程开始时定下来，之后不变：改了组织提示词、成员提示词，新开的线程才用上（团队运行里新开的卡也是），已经开着的线程不受影响，缓存不失效。
- 审查和计划评审线程带运行所属组织的链（它们按组织的规范审），不带记忆。
- 界面里能改：全体提示词（只改正文，保留frontmatter；项目里有`.xora/org.md`时提示它会覆盖）、组织提示词（组织面板里直接改）、成员提示词（成员面板里直接改，或者在编辑弹窗里改）。

## 7. 记忆：谁写、写哪、怎么读

| 记忆 | 文件 | 谁写 | 谁读 |
|---|---|---|---|
| 成员·通用 | `members/<id>/memory.md` | 成员自己（`remember`的`member`） | 它自己 |
| 成员·项目 | `members/<id>/projects/<项目>.md` | 成员自己（`project`，默认） | 它自己；别人用`recall`查 |
| 组织·项目 | `groups/<id>/projects/<项目>.md` | 组织里的成员（`team`） | 这个组织的成员；别的用`recall`查 |
| 全体·项目 | `orgs/default/memory/<项目>.md` | 直属成员的`team` | 所有成员 |

- **“当前的组织”**：在团队运行里是运行交给的那个组织，在别处是成员自己所在的组织，直属成员是全体。`team`笔记写进当前组织的项目记忆，这样“怎么构建、怎么测试”这类项目事实留在干这件活的组织里。
- **读**：线程开始时取一次快照，之后不变（1.1.0是每轮现读：记忆在系统提示词里，每写一条笔记，下一轮整段历史的缓存都失效），只带当前项目的：成员通用2000字、成员·项目3500字、当前组织的项目记忆2500字、全体·项目1500字，合计9500字（和1.1.0一样）。都取最近的，并说明别的项目、别的组织也有笔记，用`recall`查。
- **写**：规则同06第19、21节（一句话、最多500字、能替换旧的、不记密钥、文件超过16000字删最早的）。
- **查**：`recall`把组织记忆也算进来，排序：自己的 > 当前组织的 > 别的，每条写明是谁、哪个组织、哪个项目记的。
- **在界面里看和改**：成员面板“⋯→记忆”打开抽屉（沿用原来的记忆编辑器，经host排队写，不会和成员同时写冲突）；“打开目录”在访达里看文件。

## 8. 交互配合

- **用户→总助手**：唯一入口。总助手用`member_list`按需看组织树（不放进每轮的“现在的情况”），选能覆盖这件活的最小组织交给它（`team_start`带组织），一个人能做完的派给一个成员（`member_dispatch`）。
- **交给一个组织**：`leadOf`当这次的主管；干活的是这棵子树里非主管角色的成员（子组织的成员也在内），子树里一个都没有就拒绝。主管的名册层只列这些人。执行只有两层（主管→成员），多层转派以后再说：上下文层层压缩会丢细节，费用和时间翻倍。
- **升级**：成员→负责人（`ask_supervisor`、阶段评审、巡检，06第20节）→用户（只有要用户决定、或大批量删除和删库这类审批）。
- **主管代审**：成员线程里的审批由`supervisorOf(成员)`的档位挑模型来审；不是成员的线程照旧。
- **跨组织**：一个组织要别的组织帮忙，由总助手再派；成员可以用`recall`读别的组织、别的成员的笔记。

## 9. 主管评分

- **什么时候打**：团队运行的报告写好后，一次请求给这次所有做过卡的成员打分（每张卡一个分）。被取消、没开工的卡不打；派给单个成员的活、例行任务、子agent在v1里不打。设置里可以关掉（`team.scoring`，默认开）。
- **怎么打**：
  - **基础分**（host按事实算）：卡完成80分；每次退回扣5、每次升档扣5、每次巡检命中扣3，最低50；一次就通过验收加5。卡失败或受阻40分，同样扣，最低10。
  - **主管调整**：用这次运行主管的模型，给它每张卡的目标、交付摘要、还剩什么、验收结果和基础分，让它在基础分上±10并写一句理由，回json。
  - 最终分在0～100之间；失败、受阻的卡最高50。
- **状态**：运行记下`scoring`（pending、done、skipped）。应用重启后pending的补打一次；按（运行、卡、成员）去重；没有模型、请求出错、回答解析不了就记skipped，不编分数。打分的请求算进主管的用量。
- **存**：数据库表`member_scores`（成员、分数、基础分、调整、理由、谁打的、项目、运行、卡、标题、时间）。
- **显示**：成员面板显示最近10次的平均分（取整）和次数，和再往前10次比是升是降，下面列最近5次（日期、项目、任务、分数、理由）；不到3次只显示次数。树上成员行显示平均分的小徽标。

## 10. token消耗和最近参与的项目

- **记账**：`usage_events`加`member_id`（迁移6，带`(member_id, ts)`索引），记账时定：
  - 成员自己的线程（对话、例行、工作流步骤、团队卡）：`memberIdOf(线程)`（`coder-T1`算`coder`）。
  - 子agent的线程：它自己是成员就算它，否则算父线程的成员。
  - 主管代审、团队报告、评分这些直接调模型的请求：算负责的主管。
  - 以前的数据按规则回填：`agent_id`就是成员id；或者`task_id`不为空且`agent_id`是“成员id-卡号”。
- **token**：近30天和累计，各自的输入、输出（含思考）、缓存命中和花费（按设置的币种）。
- **最近的项目**：从`usage_events`按成员和项目汇总，按最近一次排，最多5个：项目名、最近一次、做过几件（同一次运行或同一个线程算一件）。删掉运行、归档线程都不影响。

## 11. 界面

- **组织架构页**（团队页的第一个页签）是一张横向的树：
  - 最左是根节点“我/总助手”：审批由谁批；“+”（组织、直属成员）、“全体提示词”。
  - 往右是组织节点：名字、一句话说明、负责人一行、组员一行一个（头像、名字、职责、评分徽标）；节点头上一直有“+”（子组织、成员）、“交给这个组织”、“⋯”（编辑、打开目录、删除）。组织可以折叠，折叠状态记在本地。
  - 直属成员在根下面的“直属成员”节点里。
  - 树太大时横竖都能滚动。
- **点组织**：右侧面板：名字、路径（研发中心/前端组）、负责人、说明、组织提示词（直接改、保存，显示字数）、子组织和组员。
- **点成员**：右侧面板，只有五块：名字（和所在组织的路径）、提示词（直接改）、最近参与的项目、主管评分、token消耗。顶上的按钮：派活、编辑、“⋯”（记忆、例行任务、打开目录、恢复默认、删除）。原来成员页的记忆编辑器、例行任务挪进“⋯”打开的抽屉和弹窗，线程列表不再显示。
- **新建组织**（弹窗）：名字、上级（默认点的那个）、一句话说明、组织提示词、负责人（已有的、没带组织的主管角色成员，或“稍后再设”）。
- **新建成员**（弹窗）：名字、所属组织（默认点的那个）、岗位（内置成员当模板，选了就带出角色、档位、权限和默认提示词；只有组织还没有负责人时才出现“负责人”，选了就成为这个组织的负责人）、提示词（按岗位预填，可改）；“更多设置”里是一句话职责、档位、模型、权限、MCP。
- 不再有“对话建人”按钮；总助手对话里照样能建人。

## 12. 协议和工具

- `OrgGroupSchema`加`parentId`（没有就是第一层），`leaderId`为空串表示还没有负责人。
- `org.saveGroup`加`parentId`、`prompt`，`leaderId`可以为空，`memberIds`不传就不变；`org.readGroup`（新）返回组织提示词和目录；`org.deleteGroup`按第4节挪；`org.root`、`org.saveRoot`（新）读写全体提示词的正文。
- `member.stats`（新）：目录、最近的项目、token（近30天和累计）、评分。
- 总助手：`group_save`加`parent`和`prompt`，负责人可以不填；`member_list`按树列出；提示词加“选能覆盖这件活的最小组织”。
- 设置加`team.scoring`。

## 13. 迁移

- 原来的小组没有`parentId`，就是第一层组织；组长就是负责人；不在组里的照旧是直属成员。
- `org.md`照旧是全体提示词；`orgs/default/memory/<项目>.md`照旧是全体·项目记忆。
- 删掉`multiple_supervisors`检查：负责人多是正常的。
- 组织目录用到时再建。

## 14. 分期与验收

1. **树和界面**：组织树的约束、groups.json v2、组织目录和提示词、全体提示词、`member_id`记账和回填、`member.stats`（token、最近项目）、横向树、组织面板、成员面板五块（评分先显示“暂无”）、两个弹窗、去掉对话建人。宿主测试：随机挪动后无环、层数不超过3、每人最多在一个组织；新旧版本都能读groups.json；`coder-2`和`coder-T1`的归属。界面冒烟：建组织、建子组织、在子组织里建成员、改组织提示词、点成员看到五块。
2. **组织链和组织记忆**：组织链提示层、团队运行按子树取人、记忆快照、组织·项目记忆的读写和`recall`、`supervisorOf`用于代审。宿主测试：提示层的顺序和长度上限、子树取人、记忆快照不随写入变。
3. **评分**：基础分、主管调整、`member_scores`、补打和去重、徽标。宿主测试：坏json、超时、重启补打不重复。
4. 总助手工具、文档（06、08、03）、readme截图。
