# 21｜agent工具第1期：调用一次就成、文件不被改坏、长命令不白跑（2026-11-12）

这份文档审查xora engine的内置工具（04第3节），记这一轮做了什么、为什么这样做、还有什么留到后面。和04第3节不一致的地方以这里为准。

## 0. 用户要求

2026-11-12用户提的：看一下现在的仓库，迭代agent工具。没有给具体条目，所以这一轮先审查、再按证据挑最值得做的。

## 1. 审查：现在的样子

### 1.1 有哪些工具，谁用得多

内置16个：`read`、`list`、`glob`、`grep`、`lsp`、`edit`、`multi_edit`、`write`、`apply_patch`、`bash`、`bash_output`、`bash_kill`、`web_fetch`、`web_search`、`todo`、`tool_output`。工具定义一共约1.7万字符（4千token上下），不算负担。host另外给线程加`agent`（子agent）、`remember`/`recall`（记忆）、主管和总助手各自的工具。04第3节表里的`browser`、`git`、`ask_user`、`plan`一直没做。

用量看20第1.1节那次统计（2026-11-10，30段对话、2888次模型请求）：`bash` 1343次、`read` 263、`web` 71、`edit` 69、`write` 48、`grep` 42。也就是说：

- **`bash`是用得最多的工具**，是`read`的5倍；上下文里大半是命令输出。
- **用的模型主要是deepseek和minimax**，不是工具格式的“母语”模型：参数名、类型、json写法都更容易出小差错。
- `write`（整文件覆盖）和`edit`用得差不多，整文件覆盖的风险比想的常见。

这一轮没有重新统计真实会话（这次会话里复制会话记录被权限层拦下了），下面的问题都是读代码加小实验复现出来的。

### 1.2 复现出来的问题

| 问题 | 怎么复现 | 后果 |
|---|---|---|
| 可选参数传`null`被拒 | `read {path, offset: null}` | 一次失败的调用加一次重试。按openai严格模式训练的模型习惯把不用的参数填成`null` |
| 数字、布尔写成字符串被拒 | `offset: "10"`、`replaceAll: "true"` | 同上。host的`agent`工具自己处理了（注释写着“模型时不时把布尔写成文本”），内置工具没有 |
| 别的工具体系的参数名被拒 | `edit {file_path, old_string, new_string}` | 同上。这些模型见过大量claude code和codex的调用记录 |
| 不认识的参数被悄悄丢掉 | `bash {command, run_in_background: true}`、`write {path, content, append: true}` | 比报错更糟：前一个在前台跑到超时被杀，后一个把文件整个覆盖 |
| 非utf-8文件被改坏 | gbk文件里改一行ascii | 整个文件的中文变成`EF BF BD`，无法恢复（只能靠检查点回滚）。读的时候显示成`���`也没有任何说明 |
| `write`盲目覆盖 | 对没读过的已有文件直接`write` | 悄悄丢内容。团队里两个成员在同一个目录干活时，一个人拿旧版本整文件写回去，会抹掉另一个人的改动 |
| `edit`对空白太严 | 文件用tab缩进、模型写4个空格；或者整块少缩进一层 | 失败，提示只说“没找到，重读文件” |
| `edit`把行号也抄进来 | `oldString`带着`read`输出的`    12<tab>` | 失败，提示里没点出原因 |
| 命令输出原样进上下文 | `\r`刷新的进度条、颜色码、同一行重复几百次 | 3万字符的额度被进度条的每一帧占掉，真正的报错被挤出去 |
| 默认超时一到就杀 | 没给`timeoutMs`的构建、测试跑过2分钟 | 白跑2分钟，模型再用更长的超时或后台重跑一遍 |
| 等后台任务只能轮询 | `bash_output`立即返回 | 模型要么`sleep`要么连续查，每查一次是一次请求 |
| `bash_kill`要审批 | 询问模式下停掉自己启动的任务 | 用户刚批准启动，停的时候又要批一次；计划模式下干脆停不了 |
| 命令可能等一个不存在的人 | `git commit`不带`-m`、`git rebase -i`打开编辑器 | 卡到超时 |

## 2. 对照

看了claude code、codex、opencode、gemini cli、cline这几家的工具层，取了这些做法：

- **入参容错**：各家多少都有（把字符串形式的数字转回去、兼容旧参数名），但都是哪里出过事补哪里。这里做成工具层之前统一的一层，按工具的schema来。
- **edit的回退匹配**：opencode有一串“替换器”（按行去空白、缩进无关、首尾锚定加相似度……），aider和cline也有模糊匹配，codex的`apply_patch`是四级宽松度。这里只取**不用猜**的那几种（见4.2），相似度匹配没有要：它会把改动放到“差不多”的地方。
- **覆盖前必须读过**：claude code的`write`和`edit`都要求先读、并且读后没被改过。这里只管`write`：`edit`和`apply_patch`是按当前文件内容匹配的，匹配得上就说明模型手里的文本是新的。
- **超时转后台**：claude code近期版本的做法。这里加了一条区分：模型自己给了`timeoutMs`就照杀（那是它要的上限），没给才转后台。

没有取的：`web_fetch`用小模型按问题摘要网页（多一次模型花费，原文更可靠，长页已经存成文件）；`bash`跨调用保留`cd`（要包一层脚本取最终目录，三种shell各写一遍，收益不大）。

## 3. 原则

1. **宽容只到“意思没有疑问”为止**：`"10"`是10，`file_path`是`path`；猜不准的（截断的json、相似但不相等的文本）照旧报错，并把能照着改的信息给全。
2. **会改东西的调用不带着误解跑**：只读工具多了个不认识的参数，照跑并说明；会改文件、会执行命令的，不跑。
3. **不动没碰的字节**：文件用什么编码、什么换行、什么缩进，改完还是什么。
4. **错误信息要能直接照着改**：失败时把文件里那几行、参数清单、现有的工具名给出来，省掉下一次读文件。
5. **工具结果给模型看的和给人看的分开**：提醒只进模型的上下文，不出现在界面的工具卡片里。

## 4. 设计

下面是第1期最终的样子。做完后请了一轮独立审查，提出的21条问题都已经改进来（第8节记了哪一条改了什么）。

### 4.1 入参容错（`packages/tools/src/lenient.ts`，引擎`prepareCall`）

模型的调用在校验之前先过一遍：

- **工具名**：大小写和分隔符不同的算同一个（`Read`、`MultiEdit`、`WebFetch`），别家的叫法映射过来（`run_terminal_cmd`→`bash`、`str_replace_editor`→`edit`、`TodoWrite`→`todo`）；只收意思唯一的名字，`search`这种不猜，一个写法对得上两个工具时（mcp的`a_b`和`ab`）也不选。之后权限、hook、记录都用工具自己的名字（引擎靠工具名是不是`bash`决定要不要把命令交给host分析，所以必须是规范名）。找不到时错误里列出现有的工具。
- **名字怎么比**：只看字母和数字，各种文字的都算，所以中文名之间不会互相混（成员名`测试`和`规划`是两个名字，`测试 `、`@测试`是`测试`）；一个字母数字都没有的名字（`!=`、空字符串）只和自己相等。
- **参数的json**：解析失败时只修读法唯一的几种——字符串里直接写的换行和tab、括号前多余的逗号、python的`True`/`False`/`None`、外面包的代码围栏、同一个对象连发几遍、后面跟着的结束标签（`</tool_call>`这类）。没有双写的反斜杠（`"\d+"`）也修，但同一份参数里还有`\b`、`\n`、`\t`这种两种读法都通的转义时不修（`"\bfoo\d"`里的`\b`是单词边界还是退格、`C:\temp\new`是路径还是tab加换行，猜错了搜索结果、路径、文件内容就是错的）。**被截断的json不补全；第一个完整的值后面还有别的内容（另一个调用的参数、引号没转义剩下的半截字符串）不丢弃**，都照旧报错，错误里提醒反斜杠和引号要转义。
- **参数名**：大小写和分隔符不同的算同一个（`old_string`=`oldString`），对得上两个参数时不动；每个工具登记别名（`file_path`→`path`、`include`→`glob`、`run_in_background`→`background`……，写在各工具定义的`lenient.aliases`里）。本名和别名都给了，以本名为准。
- **参数值**：schema不收`null`的地方，`null`当作没给（必填的不删，留给工具报错；`nullable: true`算收`null`）；文本形式的数字和布尔转成对应类型，反过来也转；列表写成了json字符串就解析，该给列表却只给了一个对象就包成列表；枚举值大小写和写法不同的归到唯一对得上的那个值（`C++`在`c`、`c++`、`c#`里是`c++`），个别工具登记同义词（`todo`的`done`→`completed`）。`anyOf`里有几个对象分支、或者有一个分支收任意字符串时，不替模型选分支，值原样传。
- **内置工具额外的三条**：可选参数给了空字符串、或者给了小于下限的非正数（`offset: 0`、`headLimit: 0`），当作没给；该给字符串列表却只给了一个字符串，包成列表（空字符串、带逗号或换行的不包：那可能是写成文本的列表，不拆）。
- **不认识的参数**：只读工具照跑，结果后面说明哪个参数没用上、工具有哪些参数；会改东西的工具不跑，直接报同样的说明。`explanation`、`reason`这类解释性参数不算。
- **个别工具自己的处理**（`lenient.adapt`、`lenient.refuse`）：
  - `bash`的`timeout`——claude code按毫秒、别家多按秒，上限10分钟。600以内只可能是秒，1万以上只可能是毫秒；中间的（`900`：15分钟，还是0.9秒）不猜，写成`"30s"`这种不是数字的也一样：参数原样留着，按“不认识的参数”处理，`bash`不执行并列出`timeoutMs`。0和负数表示不限。`bash_output`的`timeout`、`wait`同样换算。
  - `todo`的条目写成纯文本或者没写状态，算作待办。带`merge: true`（cursor的写法：只发有变化的条目，并进现有列表）时拒绝并说明要发完整列表，否则列表会被这几条整个替换掉。

host工具和mcp工具带自己的json schema：做拼写和类型上的转换（参数名和枚举值的大小写与分隔符、`null`、文本数字、json字符串、单个对象包成列表）。不做的：别名表、空字符串和0当作没给、单个字符串包成列表；不认识的参数原样传过去，由它们自己判断。

校验仍然失败时，错误信息后面附上参数清单，必填的标出来。

**历史里记的是实际执行的调用**：靠容错才成功的调用，记进会话历史时改成工具自己的名字和它实际拿到的参数（`Read {"file_path": …}`记成`read {"path": …}`）。任务账本和遮蔽占位（20第4节）按规范参数名读历史，厂商接口要合法的json，模型也会照着自己之前的调用写下一个。和原样一致的调用一个字节都不动；被拒绝的调用保持原样，和它的报错放在一起。

### 4.2 edit：找得到，找不到也说得清（`packages/tools/src/match.ts`）

精确匹配（含换行符转换）不变，永远先试。精确匹配找不到、又没开`replaceAll`时，按下面的顺序各试一遍，严格的在前：

1. 去掉从`read`输出里抄来的行号（旧文本每一行都带才算；只有带行号的空行时不定位）；
2. 忽略行尾空白；
3. 整块缩进深浅不同，用的是同一种缩进字符：去掉各自的公共缩进后逐行相等；
4. 缩进单位不同：一边tab一边空格，或者2个空格对4个空格，所有有缩进的行比例一致。两边都是空格时要求旧文本里出现过两种深度——只有一种深度时和“整块深浅不同”分不清，那种情况归第3条。

每一种都要求**除了这一种空白之外逐行相等**、**全文只有一处**符合。`newString`按同样的办法折算到文件的缩进上：整块平移时每一行移同样多（移不动的——比整块还浅、或者用了另一种缩进字符——这一处就不算）；换单位时按比例换算（3个空格对一个tab时新文本里出现5个空格，也不算）。文件用tab、模型写空格的情况一律按换单位处理，不会出现tab后面跟空格的混合缩进。

新文本里的行号只去掉和旧文本一模一样的那些前缀（照抄的行、只改了内容的行）；没带行号的新行原样写入；带着旧文本里没有、形状却一样的行号时（模型自己接着编的号，或者内容本身就以数字加tab开头）分不清，这一处不算。

有多处符合时报错并给出行号。结果里写明“`oldString`和文件不完全一致，是按……匹配的”，并照旧附上改动处的几行让模型核对。`replaceAll`只替换精确出现的地方。

没有做内容上的宽松（引号、破折号的全半角）：那会在没让改的地方改字符。`apply_patch`的四级宽松度是codex格式本身的约定，保持不变。

找不到时的错误信息改成能直接照着改的：给出文件里最像的那几行（按“去掉首尾空白后相等的行”投票定位；单行的按首尾公共部分的占比），指出第一处不同的行，两边的文本用带引号的形式并排列出（tab和行尾空格看得见），再附上那几行带行号的原文。文件在上次读过之后被别人改了，也在这里说一句。

### 4.3 命令：输出、超时、任务（`terminal.ts`、`jobs.ts`、`tools/bash.ts`、`env.ts`）

- **输出按终端显示的样子给**（`renderTerminalText`）：回车符把光标移回行首、后写的盖住先写的，退格同理；光标在行内的移动（`ESC[nG`到某一列、`ESC[nD`左移、`ESC[nC`右移）照做，`ESC[K`清行；颜色、标题这些转义序列去掉；同一行连续出现超过3次，只留一行加次数。没有这些东西的输出原样不动。给模型的文本、存成文件的全文、界面上的实时输出都是整理过的。开销和输出长度成正比，一行里清几万次也一样。
- **前台命令也是一个任务**：`bash`启动一个`ShellJob`然后等它。给了`timeoutMs`的，到时间就停（杀整个进程树），和以前一样；没给的，等满2分钟还没结束**不杀**，登记成后台任务继续跑，返回目前的输出和任务号，明确写“这不是最终结果”。原来“前台执行”和“后台任务”是两套代码、两种输出缓冲，现在是同一个类、同一种缓冲（`OutputLog`：留开头和最新的部分，可以按位置取增量）。
- **被截断的输出都存全文**：命令结束时、转后台那一刻、`bash_output`取增量时，只要超过3万字符截掉了中间，全文就存成文件并在结果里给出路径。
- **转后台的命令属于这一轮**：用户停止这一轮时，这一轮里转后台的命令一起停掉。`background: true`启动的任务是有意让它活过这一轮的（服务、监听），不受影响。引擎进程退出时，所有还在跑的任务一起结束（host不关会话，直接结束进程；以前`background: true`的任务会成为没人管的孤儿进程）。
- **`bash_output`可以等**：`waitMs`（最多10分钟）等到任务结束再回答，中途取消这一轮会立即返回。任务还在跑时，结果末尾提示可以用`waitMs`。任务失败结束时（退出码非0、被信号终止、启动不了），这次`bash_output`的结果标成失败，和`bash`等到命令结束时一样；被`bash_kill`停掉的不算失败。
- **任务账本跟着任务走**（20第4.2节）：转后台的命令在账本里写“还在跑，没有结果”，不记成成功；之后`bash_output`或`bash_kill`带来结局时，这条命令改成成功、失败（并进“未修复的失败”）或已停止，引用指向带来结局的那条结果。被遮蔽的“输出到目前为止”也标成没有结果。
- **`bash_kill`不审批，但不算只读**：它只能停本会话启动的任务，而启动时已经过了审批。它仍然按顺序执行（同一条回复里先停再查，查到的是停止后的状态），带着不认识的参数时不执行（`ToolDefinition.unasked`）。
- **不等人的环境**（`nonInteractiveEnv`）：`GIT_EDITOR`、`GIT_SEQUENCE_EDITOR`、`EDITOR`、`VISUAL`设成`true`（git用默认信息、不开编辑器），`GIT_TERMINAL_PROMPT=0`，`PAGER`和`GIT_PAGER`设成`cat`，`TERM=dumb`，`DEBIAN_FRONTEND=noninteractive`。windows上只给git自己的那几项和`TERM`（git在自带的shell里找得到`true`和`cat`，别的程序自己去启动`%EDITOR%`会找不到）。会话自己的环境变量可以覆盖它们。有了“超时转后台”之后这一条更要紧：卡在编辑器里的命令不会被超时清掉了。
- **界面**：命令卡片在任务还在跑时标注“仍在后台运行（job-n）”。没有任务列表和停止按钮：要停，停掉这一轮，或者让agent用`bash_kill`。
- **团队巡检**（06第20节）：成员用同样的参数连续`bash_output`等一个还在跑的任务，不算“重复同一个调用”；任务已经结束还反复查的照旧算。

`bash`的说明相应改了：不再让模型估超时，只在“必须在多久内停掉”时才设`timeoutMs`。

### 4.4 文件：不改坏、不盲目覆盖（`text.ts`、`tools/files.ts`）

**编码**：

- **一处判定**（`decodeFile`）：`read`显示什么、`grep`搜什么、`edit`/`write`/`apply_patch`按什么写回，用的是同一个结论。`read`先按utf-8（或者bom说的编码）流式读，不占内存；遇到不合法的字节，再把整个文件交给`decodeFile`（32mb以内；更大的按utf-8显示，并说明太大判断不了）。
- 没有bom、又不是合法utf-8的文件，如果是合法的gb18030（gbk、gb2312都包含在内），并且**解码再编码回去和原文件逐字节相同**，就按gb18030读写：`read`显示正常的中文并注明编码，写回时保持这个编码。
- **坏了几个字节的utf-8不算gb18030**：utf-8的双字节字符（带重音的拉丁字母、西里尔字母）恰好都是合法的gbk双字节，夹了一个latin-1字节的德语、俄语文件会整份“合法”。所以先看按utf-8能解出多少：解得出的非ascii字符多于解不出的字节的两倍，就是utf-8（gbk中文按utf-8解，五个字里碰巧合法的不到一个）。这种文件照utf-8显示，坏字节是`�`，拒绝改写。
- gb18030的编码表不随包带：第一次用到时拿运行时自带的解码器把双字节和四字节区全部解一遍，反过来建表（7万多项，一次几十毫秒）；其他平面按标准的线性公式算。
- 带bom的文件按bom说的编码严格解码；里面有不属于这个编码的字节，和下面一样算无法改写。
- 认不出编码的文件（latin-1、big5、shift_jis……）：`read`照旧显示（解不出的字节是`�`）并说明；`edit`、`multi_edit`、`apply_patch`**拒绝改写**，提示先转成utf-8或者用脚本按字节处理。`write`的内容里带着`�`时也拒绝（那是从`read`的显示里抄回来的，写进去就把原来的字节换成了`�`）；全新的内容可以写，结果里说明文件的编码变了。
- “往返一致才算”这条保证了不管判断得对不对，没碰的字节不会变：big5文件被当成gb18030时显示会是乱码，但改动之外的字节一个不差。
- **`grep`按文件真实的编码搜**：内置搜索直接用`decodeFile`；走ripgrep时（它把所有文件当utf-8），模式里有非ascii字符的再按gb18030查一遍，只收确实是gb18030的文件，结果和内置搜索一致；ascii模式命中的行按真实编码显示。

**覆盖保护**：

- 会话记下自己读过、写过的文件当时的修改时间和大小（`FileLedger`，按真实路径，只在内存里）。
- `write`要覆盖一个已有的、非空的文件时：这个会话没读过它，报错让先读；读过之后被别人改过（用户、另一个agent、格式化工具），报错让重读。自己刚写的文件算读过；读了一部分也算读过。新文件、空文件、内容没变的情况不受影响。
- `write`不再用文本覆盖二进制文件。
- `edit`、`multi_edit`、`apply_patch`不查这个：它们按文件当前内容匹配，匹配上了就说明没问题。但它们改完之后，**只有改之前会话就了解这个文件**（读过且没被别人改过，或者文件是它自己新建的），才把文件记成“看过现在的样子”：改一行只让模型看到那几行，没读过的文件、被别人改过的文件改完之后仍然不能整文件`write`，要先读。
- 补丁里对同一个路径先`Delete File`再`Add File`是写明了的整文件替换，不查；新内容沿用原文件的编码。
- 重启后记录是空的，第一次覆盖前要再读一遍。

### 4.5 引擎：重复调用提醒

同一轮里，同一个调用（工具和参数都相同）连续出现、结果也完全相同，第3次起每3次在工具结果后面加一段提醒：再调一次不会有变化，换参数或换办法，被卡住就说出来。结果会变的调用（轮询任务，状态行里的时长每次不同）天然不算。和计划提醒一样，只进模型的上下文，界面上的工具卡片里没有。团队里的巡检（06第20节）在更高一层管成员兜圈子，这里管的是每一个对话。

### 4.6 代码结构

- 新文件：`lenient.ts`（入参容错）、`match.ts`（宽松定位和最接近的行）、`terminal.ts`（终端输出整理）。
- 合并：`shell.ts`的`OutputCapture`和`jobs.ts`的`RollingText`合成`OutputLog`；`runCommand`删掉，前台执行改成等一个`ShellJob`。
- `ToolDefinition`加`lenient`（别名、同义值、忽略的参数、专门的处理、拒绝的理由）和`unasked`（会改东西但不用审批），`ToolContext`加`files`（文件记录）。
- 引擎：`prepareCall`接入容错层，`asRun`把执行的调用按规范形态记进历史，`EngineSession.files`，环境变量和实时输出各一行；账本和占位从`bash`的结果里认任务（`backgroundJobOf`、`jobStateIn`，和产生这些文字的代码放在一起）。
- host：巡检的调用签名提成`watchSignature`。界面：命令卡片多一行状态。协议：命令的显示数据里`background`加`running`。

## 6. 风险

- **超时转后台后模型当成跑完了**：结果里写了“不是最终结果”，账本和界面都标着还在跑；弱模型仍可能忽略，后面用真实任务看。出问题时可以把`foregroundMs`调大或者恢复成一律杀。
- **覆盖保护多一次读**：模型第一次覆盖已有文件会多一次`read`；没读过的文件`edit`之后想整文件重写，也要先读。这是有意的。
- **宽松匹配放错地方**：每一种都要求唯一并且其余逐行相等，结果里说明了匹配方式并附上改后的几行；检查点可以回滚。
- **拒绝多了一些**：json里单写的反斜杠碰上`\n`、`timeout`落在600到1万之间、`todo`带`merge`，现在都是一次报错加一次重发，换来的是不带着误解执行。
- **`TERM=dumb`让个别工具的输出变样**：少数工具在这个值下会给警告或者拒绝运行，会话环境变量可以覆盖。
- **编码判断是统计的**：别的双字节编码可能被当成gb18030（显示乱码），但字节不会被改坏。只有三到六个汉字的gbk文件约有千分之一被当成坏了的utf-8（表现为拒绝改写）；只含一两个带重音字母、又夹了一个坏字节的utf-8文件仍可能被当成gb18030。
- **历史里的调用被改写成规范形态**：只在调用和规范形态不一致时才改。个别厂商如果校验自己回传的工具调用（带签名的思考块之外），可能不认；目前接的几家没有这种校验，出问题时这是第一个要看的地方。
