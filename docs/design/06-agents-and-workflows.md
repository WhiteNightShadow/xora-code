# 06｜agent团队、任务与工作流

目标：给一个任务目标，由高质量模型的agent负责拆分和监督，性价比模型的agent做具体工作，最后验收交付。所有agent共用统一的系统提示词，同一组织共用组织提示词，每个agent再有自己的提示词。

各家的共识：

1. **主管加执行者是主流**：主管用强模型做规划、派工、验收；执行者用合适的模型做具体的事；只读的侦察用快模型。
2. **不可递归委派**：执行者不能再派工，层级最多两层，防止委派死循环和成本失控。
3. **一个任务只有一个目标、一个交付**，而且必须有验收标准。
4. **两本账**：任务账本记计划，进度账本记执行；停滞就重新规划。
5. **升级通道**：做不了就带着已有发现升到更强的档位。
6. **跨家族评审**：计划和交付由另一家族的模型来审，减少同一模型的盲区。
7. **共享看板加消息**：agent之间的消息不能代替用户的批准。
8. **提示词只是上下文，不是权限边界**：强制约束要靠权限配置、工具白名单和钩子。
9. **团队不宜大**：3～5个成员；按文件分工，避免互相覆盖；成本随人数线性增长。
10. **可以恢复**：检查点持久化，中断后从断点继续。

## 2. 组织模型

```
组织（org）
 ├─ 组织提示词：目标、规范、完成标准、沟通与升级规则
 ├─ 档位表：旗舰 / 标准 / 经济 / 快速，各自对应一条模型链
 ├─ 成员（agent）：主管、规划顾问、计划评审、侦察、执行者（按类别）、审查、专家
 └─ 预算与自主级别
项目 ──绑定──▶ 组织（一个项目用一个组织，可以切换）
```

- **存放**：
  - 用户级：`<数据目录>/orgs/<org>/`，包括`org.md`和`agents/*.md`。
  - 项目级：`.xora/org.md`和`.xora/agents/`，入库给团队共享。
  - 项目级覆盖用户级的同名项。
- **默认组织**：内置一个，开箱即用，成员和档位都配好了。

| 角色 | 职责 | 默认档位 | 权限 | 能否派工 |
|---|---|---|---|---|
| 主管 | 理解目标、澄清、拆分、派工、监督、验收、整合、写交付报告 | 旗舰 | 只读加任务工具；写操作交给执行者 | 能 |
| 规划顾问 | 复杂目标先出方案和任务图 | 旗舰 | 只读 | 不能 |
| 计划评审 | 用不同家族的模型挑计划的漏洞，只审一次 | 旗舰（跨家族） | 只读 | 不能 |
| 侦察 | 读代码、查文档、搜资料，返回事实摘要 | 快速 | 只读 | 不能 |
| 执行者 | 完成一张任务卡并交付；按类别分编码、测试、文档、前端、数据、运维等 | 经济或标准 | 按类别设定；写操作在自己的worktree里做 | 不能 |
| 审查 | 审查交付物、跑验收命令 | 标准（跨家族） | 只读，可以运行验收命令 | 不能 |
| 专家 | 处理疑难问题和升级上来的任务 | 旗舰 | 按需设定 | 不能 |

## 3. 模型档位与路由

| 档位 | 用途 | 默认模型链（示例，可改） | 思考强度 |
|---|---|---|---|
| 旗舰 | 主管、规划顾问、计划评审、专家 | `kimi-k3.1-pro` → `deepseek-v4-pro` → `glm-5.3` | high |
| 标准 | 复杂实现、审查 | `deepseek-v4-pro` → `glm-5.3` → `kimi-k3` | high |
| 经济 | 常规实现、测试、文档 | `deepseek-flash` → `glm-5.3-flash` | 按任务定 |
| 快速 | 侦察、检索、分类、摘要 | `deepseek-flash`（关思考）→ `glm-5.3-flash`（low） | 关或low |

- 档位表定义在组织层。换厂商时只改档位表，不用逐个改agent。
- 档位里也可以放外部官方agent，比如专家档用codex（经acp，走用户自己的订阅，只用于交互式任务）。

**路由规则：**

1. **默认**：角色决定默认档位。任务卡可以申请更高的档位并写明理由，由主管批准。
2. **回退**：模型链按顺序回退，遇到限速、过载、5xx时切到下一个。
3. **升级**：执行者返回`escalate`（附上已有发现），或者连续2次验收不通过，就换高一档重派；仍然不过，由主管接手或者问人。
4. **降级建议**：某类任务在某个档位上一次通过率一直很高时，提示可以改用更便宜的档位。只给建议，不自动改。
5. **预算紧张**：非关键任务可以降一档执行。
6. **跨家族**：审查和计划评审默认使用和执行者不同家族的模型。
7. **合规**：无人值守的运行不用订阅通道，api、本地模型和自定义端点都可以；订阅通道只用于交互式任务（见07）。

**缓存**：同一档位、同一角色的执行者共享"系统+用户全局+组织+项目+角色"这段前缀，并行跑同类任务时前缀缓存的命中率高。

## 4. 提示词分层：统一系统、组织、agent

| 层 | 内容 | 谁写 | 作用范围 |
|---|---|---|---|
| 第1层：系统层（xora统一） | 行为准则、工具用法、安全要求、协作协议（怎么读任务卡、怎么交付、怎么升级、什么时候提问）、交付单格式；外加按模型家族的小段适配 | xora，只读 | 所有agent |
| 第2层：用户全局层 | 个人偏好，比如回复用简体中文 | 用户 | 所有agent |
| 第3层：组织层 | 组织的目标和规范：代码风格、完成标准、审查标准、沟通规范、升级政策；主管额外拿到名册摘要（谁擅长什么、用哪个档位） | 组织维护者 | 该组织的所有agent |
| 第4层：项目层 | `AGENTS.md`层级、个人项目说明 | 团队、用户 | 该项目 |
| 第5层：agent层 | 角色职责、工作方法、输出要求、禁忌 | 用户或模板 | 单个agent |
| 第6层：任务层（放在第一条user消息） | 任务卡（目标、上下文包、约束、验收标准、预算、交付格式），加环境信息 | 主管或用户 | 单个任务 |

- **顺序**：按1→6拼装。1～5放进system，6放进第一条user消息，保证前缀稳定、缓存友好。
- **冲突**：越靠后越优先，但系统层的安全要求和协作协议不能被覆盖。
- **强制约束**：提示词只是上下文，不是权限边界。工具白名单、权限档、路径边界、预算都由host强制执行。
- **可查看**："查看生效提示词"能看到某个agent在某个任务上完整的6层内容。

和08的关系：08第1节是单线程场景下的分层；在团队里，"模式层"由agent层代替，"会话层"由任务层代替。

## 5. 主管-执行流程

```
目标
 │
 ① 澄清：主管判断目标是否清楚，必要时问用户（问题要少）
 ② 侦察：快速档、只读，可以并行 → 事实摘要
 ③ 规划：主管或规划顾问 → 任务账本：目标、事实、假设、方案、任务图、每张任务卡的验收标准、预算分配
 ④ 计划评审：跨家族，只审一次 → 主管修订
 ⑤ 计划确认：按自主级别决定，默认要人确认
 ⑥ 派工：任务卡交给执行者；每人一个独立上下文，写操作各占一个worktree，互不依赖的任务并行
 ⑦ 执行 → 交付单
 ⑧ 验收：先跑验收命令，再由审查agent或主管看证据
     ├─ 通过 → 完成
     ├─ 不通过 → 带具体意见退回（最多2轮）→ 升档重派 → 主管接手 → 问人
     └─ 执行者主动升级 → 带着已有发现升档重派
 ⑨ 进度账本：每个事件之后检查——完成了吗、在推进吗、是不是在打转、下一步派给谁、指令是什么
     └─ 连续3次没有进展 → 回到③重新规划
 ⑩ 整合：按依赖顺序合并worktree，跑全量验收，处理冲突
 ⑪ 交付报告 → 用户验收 → 归档；可以沉淀为工作流或skill
```

- **主管上下文保持干净**：主管只看交付单和摘要，不读执行者的完整过程；需要时可以展开查看。
- **监督开销**：统计主管（旗舰档）花费占总花费的比例，默认提示线是25%（可调）。超过时提示：任务可能拆得太碎，或者来回沟通太多。

## 6. 数据契约

**任务卡**：

```json
{
  "id": "T3",
  "title": "后端：短信验证码发送与校验接口",
  "goal": "新增发送和校验接口，带过期和防重放",
  "category": "coding",
  "tier": "economy",
  "assignee": "coder-1",
  "dependsOn": ["T1"],
  "context": {
    "files": ["src/auth/**"],
    "facts": ["短信封装在src/infra/sms.ts", "限流用现有的rateLimit中间件"],
    "links": []
  },
  "ownership": ["src/auth/sms/**", "src/routes/auth.ts"],
  "constraints": ["不改公共接口的已有字段"],
  "acceptance": [
    { "type": "command", "run": "pnpm test src/auth" },
    { "type": "review", "by": "reviewer" }
  ],
  "deliverable": { "kind": "code-change", "artifacts": ["diff", "testReport"] },
  "budget": { "cost": 3, "currency": "CNY", "maxTurns": 40 },
  "workspace": "worktree"
}
```

**交付单**：

```json
{
  "taskId": "T3",
  "status": "done",
  "summary": "新增两个接口，验证码5分钟过期，同一号码60秒内只能发一次",
  "changes": [{ "file": "src/auth/sms/verify.ts", "kind": "added" }],
  "evidence": [{ "type": "command", "run": "pnpm test src/auth", "exit": 0 }],
  "risks": ["短信服务商的错误码没有全部映射"],
  "openQuestions": [],
  "escalate": null,
  "usage": { "cost": 1.2, "currency": "CNY" }
}
```

- `status`可以是`done`、`partial`、`blocked`、`escalate`。
- `ownership`是派工时划定的文件范围；越界的改动在验收时标红。
- **任务账本**：目标、事实、假设、方案、任务图、关键决定、风险、预算计划；每次修订保留版本。
- **进度账本**：每条记录时间、是否完成、是否在推进、是否打转、下一步负责人、指令、理由。

## 7. 协作与通信

- **看板**：任务状态的唯一来源，记录状态、依赖、认领（加锁）、负责人。
- **消息**：
  - agent之间可以发消息，全部记录在案。
  - 默认执行者只和主管通信。调研和排障类任务可以打开"互相质疑"模式（参照claude code用竞争假设排查根因的用法）。
- **消息不是授权**：agent发来的消息不能代替用户的批准，也不能用来绕过另一个agent被拒绝的操作。
- **团队对话（2026-10-30实现）**：一次运行里的消息按时间记一份，团队视图的“对话”页签里能看到，也能给主管或某个任务发消息：发给主管的会唤醒它处理，发给成员的在它下一轮开始时带上，同时告诉主管。用户的话是指示，不是对某个操作的批准。
- **竞争假设（2026-10-30实现）**：开团队时选“竞争假设”。主管先在账本里写下2～4个互斥的假设，每个假设一张只读调查卡（类别research），交付单写支持和反对的证据；成员可以用`challenge`工具质疑别的调查卡（每张卡最多3次），对方下一轮在交付单里回应；主管按证据在账本的决定里记下每个假设成立还是被否定，再决定建修复卡还是直接交结论。
- **交接**：转交任务时附上摘要（目标、已经做了什么、产出物在哪、还有什么没做），接手方在自己的上下文里继续。
- **文件分工**：主管派工时给每个执行者划定文件范围，避免并行时互相覆盖。

## 8. 质量门与自主级别

**质量门**（对应claude code的TaskCreated、TaskCompleted、TeammateIdle钩子）：

- 任务创建时：没有验收标准的任务卡直接拒绝。
- 任务完成时：自动运行验收命令。
- agent准备空闲时：如果它的待办还没做完，就打回去继续。

**证据优先**：交付单里写"已完成"，必须附证据，比如命令输出、diff、截图。

**自主级别：**

| 级别 | 需要人确认的事 |
|---|---|
| L0 | 每一步 |
| L1（默认） | 计划、高风险动作、最终交付 |
| L2 | 高风险动作、最终交付 |
| L3 | 只看交付报告；不用订阅通道，必须设预算，权限受限 |

高风险动作包括推送、发布、删除、对外发消息、付款，在任何级别下都要走审批。

## 9. 失败处理与恢复

- **执行失败**：先退回重做（附意见），再升档，再由主管接手，最后问人。
- **停滞**：进度账本连续3次没有进展，就重新规划（次数可调）。
- **预算用完**：暂停，询问是追加预算还是缩小范围。
- **模型出错**：按模型链回退。
- **应用重启**：从账本和事件日志恢复，已完成的任务不重跑。
- **不可递归委派**：只有主管能派工，层级最多两层（主管→执行者）。

## 10. 编排模式

| 模式 | 适用场景 | 参考 |
|---|---|---|
| 主管-执行（默认） | 一个目标，拆出多种子任务 | magentic-one、crewai hierarchical、claude code agent teams |
| 顺序流水线 | 步骤固定，比如需求→设计→实现→测试 | metagpt的sop、adk的顺序agent |
| 并行扇出-汇总 | 互不依赖的子任务、多方案对比（best-of-n） | adk的并行agent、cursor的best-of-n |
| 生成-评审循环 | 对质量要求高的产出 | openai agents sdk的评审循环 |
| 竞争假设 | 根因不明的排障、调研 | claude code agent teams的用法 |
| 交接 | 按问题类型转给专家直接处理 | openai agents sdk的handoff |

固定工作流和动态编排可以互相嵌套：工作流里的一步可以是"让主管编排"，主管也可以调用一个现成的工作流。

## 11. 工作流（固定编排）

存放在`.xora/workflows/<name>.yaml`，入库共享，有schema校验和编辑补全。项目里的工作流要项目受信才能运行（手动、自动、作为子工作流都一样）；列表把“未信任”单独标出来，不算文件问题。看板上可以删除工作流：删的是文件，运行记录保留；还有没结束的运行时拒绝删除，先停止再删。

```yaml
name: bugfix-pipeline
title: 缺陷修复流水线
org: default
trigger:
  manual: true
  schedule: "0 2 * * *"          # 可选；定时运行不用订阅通道
  offPeakOnly: true              # 只在厂商空闲时段运行
inputs:
  issue: { type: string, description: 问题描述或链接 }
budget: { perRun: 20, currency: CNY }
steps:
  - id: reproduce
    agent: debugger
    tier: economy
    task: "复现问题：{{inputs.issue}}，写出一个会失败的测试"
    outputs: [testFile]
    verify: { command: "pnpm test -- {{steps.reproduce.outputs.testFile}}", expect: fail }
  - id: fix
    type: supervise                # 这一步交给主管动态编排
    needs: [reproduce]
    goal: "修复问题，让{{steps.reproduce.outputs.testFile}}通过，且不破坏其他测试"
    verify: { command: "pnpm test" }
  - id: review
    agent: reviewer
    needs: [fix]
    task: "审查fix这一步的全部改动"
  - id: approve
    needs: [review]
    gate: human                    # 人工确认后才继续
  - id: pr
    agent: coder
    needs: [approve]
    task: "提交并开pr"
```

- **步骤类型**：agent任务、主管编排（`supervise`）、并行组、人工关卡、条件分支、脚本、子工作流。
- **输入输出**：步骤可以声明`outputs`，agent用结构化结果返回，后面的步骤可以引用。
- **失败策略**：重试、升档、换agent、跳过、终止整个运行。
- **做不到就报受阻**：agent用step_result交结果。做不到这一步（缺工具、工具被拒绝、要用的输入或文件不存在等）时填`blocked`写明原因，不能当作完成交差；交了blocked的步骤直接算失败，原因就是blocked的内容（不再追要缺的outputs），之后照常走失败策略。
- **运行**：
  - 每次运行有一个运行id，每一步对应一个任务线程。
  - 中断后从未完成的步骤继续，已完成的不重跑。
  - 运行记录里能看到每一步由谁做、用了什么、花了多少、谁批准的。
  - 运行页和团队视图一样以概览为主：执行流图、进度、产出的文件、每一步的结论、时间线；另有按状态分列的看板和步骤明细（界面见03）。
- **创建方式**：手写yaml；用对话生成草稿；把成功完成的线程"沉淀为工作流"或"沉淀为skill"；可视化编辑器放到1.0之后。

## 12. 定时与触发

- **触发方式**：
  - 1.0：手动、定时（cron）、文件变化、git事件（新提交、新分支）、本机webhook（只监听127.0.0.1，带token）。
  - 1.0之后：外部渠道的消息（飞书、钉钉、企业微信、slack、github）。
- **执行条件**：应用在托盘运行时才生效；错过的定时任务按策略补跑或跳过。
- **峰谷调度**：不急的任务可以设成只在厂商空闲时段运行。比如deepseek工作日9–12点、14–18点以外是半价（见11）。
- **合规**：定时和触发运行属于无人值守，不用订阅通道（api、本地模型和自定义端点都可以，2026-10-30用户确认）。

**实现（2026-10-30）**：`packages/workflows/src/cron.ts`（cron）、`packages/host/src/triggers.ts`（`TriggerService`）、`tree-watch.ts`（目录监听）、`off-peak.ts`（峰谷）。触发器只负责"该启动了"，启不启动、排队、等空闲时段由工作流服务决定。

- **cron**：五段（分、时、日、月、周），支持`*`、列表、范围、步长、jan–dec和sun–sat、0和7都算周日，以及`@hourly`、`@daily`、`@weekly`、`@monthly`、`@yearly`；日和周两段都受限时按crontab(5)只要满足一段。按`timezone`（缺省用系统时区）的墙上时间算。cron写错、时区不认识，校验时报在`trigger.schedule`、`trigger.timezone`上。
- **夏令时**：按rfc 5545处理。跳过的钟点按跳变前的偏移换算，顺延一个跳变长度执行（纽约2:30→3:30），和本来就有的时间重合时只算一次；回拨重复的钟点只在第一次出现时执行。每天的任务不漏跑、不重跑，每小时的任务也不会多跑；回拨那一小时里，每15分钟一次的任务只跑第一遍。
- **错过的定时**：过了5分钟以上才发现的定时时间（应用没运行、系统睡眠）算错过。`missed: skip`不补；`once`在启动或唤醒时补跑一次，只补最近的那次，触发里带`missed: true`。启动时依据工作流服务记下的`lastScheduledAt`，只在这个工作流第一次交给触发器时回看，改了定时规则不回看。计时器最长60秒，每次都对墙上时间，系统睡眠、调系统时间都不会漏判，也不会重复触发同一时间。
- **文件变化**：macos和windows用原生的递归`fs.watch`；linux上node的递归监听会同步遍历整棵目录树、给每个文件加监听，所以改成每个目录一个监听，不进`.git`和`node_modules`，最多1万个目录。路径和忽略规则跟任务卡的`ownership`写法一样；`.git/`和`node_modules/`下的变化一律不算。匹配的变化停下`debounceSeconds`秒后触发一次，带上变化的相对路径（最多200个）。工作流运行时用`muteFiles`静音它的项目，解除后再静音2秒，自己改的文件不会再触发自己。
- **git事件**：默认每30秒跑一次`git for-each-ref refs/heads`，第一次是基线。被监视的分支（`branches`为空表示全部，可以写glob）提交变了触发`commit`，出现新分支触发`branch`；只监视提交时，新分支带来没见过的提交也算一次提交。一次轮询每个触发器最多触发5次。工作流自己提交时用`muteGit`，期间的提交并进基线。
- **webhook**：第一次用到时在127.0.0.1上起http服务，默认随机端口，也可以指定，被占用就换一个。`POST /hooks/<key>`，带`Authorization: Bearer <token>`，token按常数时间比较；请求体是json或文本，最多64kb；同一个key在5秒内只触发一次，多的返回429；先回202再触发。`Host`头不是本机地址的请求直接拒绝，防dns重绑定。请求体是不可信输入。
- **峰谷**：metering的`offPeakStart`算出几条时段规则同时处于空闲时段的最早时刻，8天内没有就返回空；host的`offPeakStartFor`按运行要用的模型，从各自的价格表找到时段规则。
- **接入（10-30）**：host启动时、启用或停用自动运行时、以及每60秒，把已启用且文件没改过的项目工作流交给触发器；触发后由工作流服务做无人值守检查再启动。定时触发的时间存回`last_scheduled_at`，webhook端口存在`host_values`里，重启后地址不变。工作流运行期间同时静音它项目的文件和git触发。工作流列表里显示下次定时运行的时间和webhook地址。
- **还没做**：linux上逐目录监听的代码只在macos上跑过测试。

## 13. 团队视图

- **概览**（默认页签，2026-10-31用户定：用户只看管理agent的反馈、工作agent的结论和进度报表）：
  - 进度：阶段条（规划→确认计划→执行→整合→交付）、完成几个任务、用时、花费和预算。
  - 管理agent的反馈：主管每一轮结束时说的最后一段话，最新的放在最上面，更早的可以展开。
  - 工作agent的结论：每个任务一张卡，写明执行者、档位、状态、交付单里的结论、改了哪些文件、验收结果。
  - 进度报表：各状态的任务数、进度账本的时间线，交付后可以跳到交付报告。
  - 输入框：运行中给主管发指示；运行结束后接着这次继续，新运行的主管会拿到上一次的目标和交付报告。
- **需要你确认**：这次运行各线程里待审批的事项（计划、成员的命令、交付）都列在团队视图顶部，直接在这里处理。
- **名册**：每个agent的状态、当前任务、档位、今日花费、一次通过率。
- **看板**：按状态分列，显示依赖连线。
- **账本**：任务账本的各个版本；进度账本的时间线（每次派工、验收、升级、重新规划）。
- **成本**：按档位、按agent拆分，显示监督开销占比。
- **交付报告**：做了什么、证据、花费明细、遗留问题。

## 18. 实现落点（2026-10-30）

- **代码**：`packages/workflows`（纯逻辑）、`packages/host/src/team.ts`（`TeamService`）、`team-agents.ts`（工具schema、各角色提示词、组织加载）、`team-store.ts`（sqlite，migration 2的`team_runs`和`team_board_events`）。
- **组织**：用户级在`<数据目录>/orgs/default/`（`org.md`、`agents/*.md`），项目级是`.xora/org.md`和`.xora/agents/*.md`，项目受信后才生效（项目文件能改档位和工具白名单）。
- **工具**：主管有task_create、task_assign、task_update、task_list、send_message、ledger_update、request_review；执行者有deliver、escalate、ask_supervisor（挂起等主管回答）。
- **派工**：同时工作的成员数是设置项（设置→通用→团队并发数，1～8，默认3），每次派工时读取，改了对正在跑的团队马上生效；写任务各占一个worktree，都从运行开始时的HEAD建；有依赖的任务先把前置任务的结果带进来；卡片写`workspace: 'local'`的直接在项目目录里改。
- **计划评审**：主管的计划做完、确认之前，host让计划评审成员在另一家族的模型上只审一次（同一档位的模型链里挑，项目目录、只读），评审意见作为团队更新交给主管修订一轮，然后才去确认（不需要确认的自主级别直接派工）。组织里没有计划评审，或者没连接其他家族的同档模型时跳过，运行里留一条警告。
- **确认**：计划确认、交付确认都复用审批卡片，挂在主管线程里；L1确认计划和交付，L0每次派工也确认。
- **高风险动作**：团队线程（主管、成员、审查）里的推送、发布、工作区外或整个工作区的删除、对外发消息、付款，在任何自主级别、任何权限模式下都要人确认：总是允许的规则、本会话允许、hook的免确认、全权模式都不算数，卡片上只有允许一次和拒绝，标题写明是哪类高风险动作；计划模式和拒绝规则照样直接拒绝。命令在`splitShellCommand`的切分上识别：`git push`（含`git -C x push`）、`gh pr merge`、`gh release create`、npm、pnpm、yarn、bun、cargo、twine、poetry、uv、gem、mvn、gradle的发布和release、deploy类脚本、`docker push`、kubectl、helm、terraform和云厂商cli的部署与删除、工作区外或整个工作区的`rm -rf`、`git clean -f`、`find -delete`、curl、wget、httpie向其他主机发数据（支付接口算付款）、mail、scp和rsync上传；会穿过sudo、env、xargs、npx、`sh -c`、eval、ssh，here-document和命令替换里的也能读到。mcp工具按名字里的动词和对象判断（merge、post_message、create_refund这类）。验收命令同样处理。
- **回合预算**：卡片的`budget.maxTurns`是执行者为这张卡最多能发的模型请求数，按一次派工算，同一线程上退回重做的也算在内，升档或重派后重新计；卡片没写时用host的默认值80。用完时引擎停下这一轮，这次尝试记为失败，不在这一档重试，直接走升档→交主管→问人；执行者的第一条消息里写明它的预算。
- **mcp工具**：按agent的工具白名单给：`mcp`是全部服务器，`mcp__服务器`是一个服务器，`mcp__服务器__工具`是一个工具，可以用`*`。默认名单里只有执行者和专家有`mcp`，主管、规划顾问、计划评审、侦察、审查默认没有；自己写了`tools`的agent文件要把mcp工具列出来。线程只启动用得上的服务器，名单外的mcp工具调用直接拒绝，名单内的每次调用仍走权限策略。
- **验收与升级**：验收命令按`execute`过权限策略；命令通过才开跨家族审查；退回最多2轮，再按`shouldEscalate`升档、交主管或问人。
- **整合**：按依赖顺序把worktree应用回项目，冲突就暂停问人；全量验收不过时运行结束为失败，报告照常生成。
- **重启**：未结束的运行标成已暂停，用`team.resume`继续；已完成的任务不重跑。
- **还没做**：高风险动作只在团队线程里强制确认，普通线程照旧按权限模式；写在脚本文件、别名里或编码过的命令识别不到。计划评审只在计划评审成员自己档位的模型链里找其他家族的模型。
