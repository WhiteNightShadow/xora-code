# 08｜上下文管理

## 1. 提示词分层

### 1.1 层次和存放位置

| 层 | 作用范围 | 存放 | 维护者 | 生效时机 |
|---|---|---|---|---|
| 系统（xora统一） | 所有会话和agent | 引擎内置：行为准则、工具用法、安全要求、协作协议、交付单格式；按模型家族的小段适配 | xora | 只读，可以查看 |
| 用户全局 | 本机所有项目 | `<数据目录>/prompts/global.md` | 用户 | 新会话 |
| 组织 | 该组织的所有agent | `org.md`（用户级目录或项目里的`.xora/org.md`，见06） | 组织维护者 | 新会话 |
| 项目·共享 | 一个仓库 | 仓库里的`AGENTS.md`层级（生态通用，不另造文件） | 团队，入库 | 新会话 |
| 项目·个人 | 一个项目，只对自己 | `<数据目录>/projects/<projectId>/instructions.md`，不写进仓库 | 用户 | 新会话 |
| agent | 单个agent，或当前模式 | agent定义的正文（见06），或计划、审查等内置模式 | 用户或模板 | 新会话、切换时 |
| 会话 | 一个线程 | 线程元数据 | 用户（新建时或中途） | 见1.3 |
| 任务与动态上下文 | 当前这一轮 | 任务卡、环境信息、@引用、诊断 | 主管、用户、自动 | 每轮 |

冲突时越靠后越优先，但系统层的安全要求和协作协议不能被覆盖。权限和安全规则由host强制执行，不靠提示词。

### 1.2 拼装顺序

```
[system]
  系统层（xora统一）                          ← 最稳定，所有agent相同
  <user_global_instructions>
  <org_instructions org="…">                 ← 同一组织的agent相同
  <project_instructions source="AGENTS.md路径列表">
  <project_private_instructions>
  <agent_instructions name="…">              ← 同一角色的agent相同
  <session_instructions>
[第一条user消息]
  <task_card>（团队任务时）
  <environment> os、shell、日期、cwd、git分支和状态
  用户输入，加上@引用的内容
```

变化少、共享面大的层放在前面：所有agent共享系统层，同一组织共享到组织层，同一项目共享到项目层，同一角色共享到agent层。这样并行的执行者能尽量命中前缀缓存。日期、git状态这类每次都会变的信息放在第一条user消息里。

语言服务器的诊断不单独成层：xora engine在edit、write、apply_patch成功后，把服务器报的新错误附在这次工具结果的后面（见04第3节），和其他工具结果一样参与第1、2级裁剪，不影响前缀缓存。

### 1.3 不同引擎上的实现

- **xora engine**：完全按1.2拼装，每层单独计算长度。中途修改会话提示词时不重写历史前缀，而是在下一条user消息前插入"会话说明已更新"段，保住缓存。用户也可以选择"按新提示词重建上下文"。
- **grok build**：用户全局、组织、项目·个人、agent、会话这几层拼成一段，经session/new的`_meta.rules`传入（grok以`<human_rules>`追加）；项目·共享层由grok自己读。`_meta.rules`只在创建时生效，中途修改要新开线程或分叉。不用`systemPromptOverride`，它会整体替换grok的基础提示词。
- **其他外部agent**：在首轮prompt前置一段带来源标注的`<instructions>`。不往仓库里写它们各自认的文件，避免污染仓库。

### 1.4 界面

- **设置→提示词**：编辑全局提示词，显示字数和token估算。
- **项目设置**：列出检测到的AGENTS.md层级（只读预览，可以一键打开编辑），并提供个人项目提示词编辑器。
- **线程顶部的"提示词"抽屉**：编辑会话提示词。
- **"查看生效提示词"**：按层展开，标注来源路径、长度、是否被截断。
- **预设**：保存常用组合（比如"中文回复+先计划后动手"），新建线程时选用。

## 2. 上下文预算

- **软窗口**：每个模型都有窗口和输出上限。xora engine按软窗口管理，取模型窗口和用户设置的成本窗口中较小的那个。例如1m窗口的模型默认软窗口为256k，避免长上下文费用失控。
- **计数**：上一次请求之前的部分，以厂商返回的输入token数为准；之后新加的消息按字符估算（ascii每4个字符算1个token，其他字符每个算1个）。刚压缩或清理过、上下文变小时，按上一次请求时“实际/估算”的比例换算估算值。
- **输出预留**：给回复预留模型输出上限和32k中较小的那个，但最多占软窗口的四分之一。原来软窗口设成32k时，预留就把窗口占满了，每次请求前都要压缩（10-31评测发现）。

## 3. 压缩策略（由轻到重）

| 级别 | 触发 | 做法 | 对缓存的影响 |
|---|---|---|---|
| 第1级：写入时裁剪 | 每次工具返回 | 超过阈值（比如2万字符）时只保留头尾和摘要，完整输出存为artifact，agent可以按id再读 | 没有影响 |
| 第2级：旧结果清理 | 占用超过60% | 把较早轮次的工具结果替换为一行占位，保留调用本身和结论 | 前缀变化一次 |
| 第3级：摘要压缩 | 占用超过80%，或手动`/compact` | 用快速模型把较早的部分压成结构化摘要（目标、决定、改过的文件、未完成事项、当前状态），开新上下文。轮次够时保留最近2轮原文；只有一轮时（agent在一轮里连续调很多次工具），在这一轮内部切，保留最后3步原文，并把这一轮的原始请求逐字附在摘要后面 | 重建缓存 |
| 第4级：换模型压缩 | 跨厂商切换模型 | 先做摘要再切 | 重建缓存 |

补充规则：

- **后台预压缩**：接近阈值时提前在后台生成摘要，到点直接替换，不卡用户。
- **思考内容**：deepseek带工具时，历史reasoning必须完整回传，所以不能在链条中途删除，只能在第3级压缩时整体换掉。
- **可回看**：日志只追加，压缩不删原文。界面可以展开被压缩的部分；压缩点可以撤销，回到压缩前继续（需要更大的窗口）。
- **子agent隔离**：探索类任务交给子agent，主线程只拿结论，减少压缩次数。
- **手动压缩**：`/compact`可以附带重点说明，比如"保留接口签名相关的结论"。
- **记忆建议**：压缩摘要可以提出记忆建议（见第4节）。

## 4. 记忆

- agent提出"记住某件事"时只生成建议，用户确认后才写入，写入位置由用户选：个人项目提示词，或`AGENTS.md`。
- 全局记忆写进全局提示词里的"记忆"段。
- 常驻agent有自己的记忆层（职责相关的经验和偏好），见06。
- 界面可以查看、编辑、删除；不做静默的自动写入。

## 5. 缓存友好

- system前缀保持稳定，按1.2的顺序；动态信息放在第一条user消息里。
- 会话内不改思考强度（改了kimi的缓存会失效）。
- kimi可以把`prompt_cache_options.ttl`设为1小时。缓存写入单独计费，所以按会话预计时长决定。
- deepseek和glm是自动前缀缓存。走anthropic兼容端点时，要注意`cache_control`是否被忽略（deepseek会忽略）。
- 计量里单独统计缓存命中率，在用量面板展示（见11）。
